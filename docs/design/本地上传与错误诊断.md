# 设计：本地上传与错误诊断

> 板块：咕咕点歌台 · 设计层 · 对应功能规格 `docs/requirements/specs/本地上传与错误诊断.md`（F1–F10）

## 1 方案与理由

### 1.1 一句话

把「一次上传」从「一串裸 XHR + 一个百分比」改成一台会上报阶段、会判断停滞、一定进终态的上传状态机（`public/lib.js`）；界面只按状态机报的阶段渲染（`public/app.js`）；上限与格式由 `public/engine.js` 既有的 `/api/health` 轮询带出来；服务端在每个中断与拒绝点落结构化日志（`server/index.js`）。

对齐：分片协议（4MB 切片、409 续传、410 重启一次）与日志函数 `log` / `logError` / `logQuiet` 一律沿用，不新造。

偏离一：`uploadTrack` 的入参加一个 `onState` 回调。现有 `onProgress(pct)` 只装得下一个百分比，F1 要阶段、F2 要停滞、F3 要重试次数，一个数装不下。

偏离二：`xhr.timeout` 定 30 秒（依据 public/lib.js「const REQ_TIMEOUT = 30000;」），与 F2 的「单个请求超时上限 30 秒」一致；只靠 4 分钟超时，一个请求就吃掉 F2 允许的全部等待，界面在传输中看不出进展。

### 1.4 数据事实核查

- **服务端默认上限 80MB，可被环境变量覆盖** —— 成立。依据 server/index.js「const MAX_UPLOAD = Number(process.env.MAX_UPLOAD_MB || 80) * 1024 * 1024;」
- **`/api/health` 已返回上限** —— 成立。依据 server/index.js「maxUpload: MAX_UPLOAD,」
- **服务端白名单 9 项，键带前导点** —— 成立。依据 server/index.js「".mp3": "audio/mpeg",」，九项为 `.mp3` `.m4a` `.aac` `.ogg` `.oga` `.opus` `.wav` `.flac` `.webm`
- **现有 `data/server.log` 里没有上传事件行** —— 读数：6615 行，含 ASCII `[upload]` 的行 0 条；事件行一律以 `[upload]` 起头，故事件关键词（`chunk-abort` / `reject-size` / `commit-fail`）命中同为 0。
- **分片与收尾路由无结构化留痕，仅两条通用错误转储** —— 成立。分片读体失败分支直接回错不写日志，依据 server/index.js「return json(req, res, err.statusCode || 400, { error: err.message });」；写盘失败只调一次 `logError("[upload]", err);`；收尾同样只在改名失败处调一次，成功路径记的是中文行 `[上传]`。
- **分片读到半路断开时服务端已能识别** —— 成立。依据 server/index.js「req.on("aborted", () => fail(Object.assign(new Error("连接中断"), { statusCode: 400 })));」—— 识别到了，但没留痕。
- **收尾的「空文件」分支在 HTTP 面不可达** —— 成立。上传记录只在分片非空之后创建，依据 server/index.js「if (!buf.length) return json(req, res, 400, { error: "空分片" });」，`st.size` 从第一片起就不再为 0；0 字节文件客户端不发分片、直接收尾，此时没有记录，走 410 过期分支。

上表每条的读数都是读文件直接看到的行，不是推的。

### 1.5 每个新增分支的依据

- **传输或收尾途中 30 秒无字节推进 → 中止当前请求并计入重试** —— 现场报告：歌曲拖进面板后导入进度到 100% 就不再动，报告者称自己网络很卡，且服务端没有任何报错日志。读数：单个请求的超时上限 30 秒（依据 public/lib.js「const REQ_TIMEOUT = 30000;」），停滞判定同等 30 秒（依据 public/lib.js「const STALL_MS = 30000;」）。不设看门狗时，超时到点前哪怕一个字节都没推进也只会一直等，收尾再叠上多次重试，界面就停在 100% 上没有任何可读原因。复现形态：同一份 12MB 文件用 `curl` 逐片传，每片加 `--limit-rate 8k`，界面停在 100% 超过 30 秒。
- **请求被中止（`onabort`）→ 进失败终态** —— 现场报告同上：界面永久停住且没有任何日志，说明没有异常被抛出。代码读数：四个出口各有落点 —— 超时依据 public/lib.js「xhr.ontimeout = () => finish(reject, Object.assign(new Error("网络超时"), { net: true, stall: true }));」，中止依据同组的「: finish(reject, Object.assign(new Error("上传已中止"), { aborted: true }));」。少任何一个，浏览器中止请求时 Promise 永不 settle。复现形态：上传中关掉面板再打开。
- **收尾期间进度上限 0.99，收尾成功才置 1** —— 规格 F1：100% 只在服务端确认入库后出现。读数：进度按已收字节算并封顶 0.99，依据 public/lib.js「const pctOf = (received) =>」与「const PCT_CAP = 0.99;」，100% 只留给 `done`；不封顶时最后一片一开始发，进度就到 1，剩下的等待全在 100% 上。
- **超限 / 格式不符 / 0 字节在发第一个字节前拦下** —— 读数：`curl` 分片循环传 84MB，服务端在累计满 80MB 的那一片才回 413；报告者网络卡，等于先白传 80MB 才看到报错。0 字节文件的现状是客户端不发分片、直接收尾，服务端没有上传记录，依据 server/index.js「if (!st.size) {」与「上传已过期，请重新上传」两行，用户看到的是「过期」而不是「文件是空的」。
- **诊断条目在客户端留一份** —— F8 要求在界面上看到。读数：`public/engine.js` 读 `/api/health` 失败时只把 `connected` 置 false，界面没有任何可读原因。
- **上限与格式由 `/api/health` 带出，选择器 `accept` 同源** —— 读数：上限已在该接口，依据 server/index.js「maxUpload: MAX_UPLOAD,」；服务端白名单 9 项，选择器 `accept`、界面文案与接受判定三处都从同一份 `formats` 派生，写死清单已删 —— 写死的 6 项里 aac / oga / opus / webm 用户选不到。

## 2 接口契约

### 2.1 前端

`uploadTrack({ roomId, token, file, duration, folder, limits, onState }, deps?)` → `Promise<track>`。

- `onState({ phase, pct, retry, received, total })`，`phase ∈ prepare | sending | committing | stalled | done`。`prepare` 在构造第一个请求之前发出一次。
- `pct`：`sending` 段是 `0.99 × 已发字节 / 总字节`；`committing` 段恒 0.99；`done` 才是 1。
- 重试口径：每个步骤最多重试 4 次，即含首次共 5 次尝试，分片与收尾同一口径。第 5 次尝试仍失败即进失败终态。
- 失败时 reject 一个 `Error`：`message` 是给用户看的中文整句；附加字段 `{ phase, pct, retry, aborted?, net?, status?, expired? }`。
- **发送前校验在 `uploadTrack` 内做，不在 `doUpload`**，在发出第一个请求之前判完：
  - `file.size === 0` → 一律拒绝，与 `limits` 有无无关；message 写「文件是空的（0 字节）」。
  - `limits` 有值时再判扩展名与大小：文件扩展名小写后不在 `limits.formats` 内 → 拒绝，message 列出 `formats` 的支持清单；`file.size > limits.maxUpload` → 拒绝，message 写「文件 NMB 超过上限 MMB」。
  - `limits` 未传（`/api/health` 取不到）→ 只做 0 字节这一条，格式与大小交给服务端判。
  - 拒绝时 `onState` 一帧都不发，`err.phase` 为 `"prepare"`，`deps.createXhr` 零次调用。
- **测试缝**：`deps` 可选，字段 `{ createXhr, now, setTimer, clearTimer }`，缺省回落生产实现（分别对应 `() => new XMLHttpRequest()` / `Date.now` / `setTimeout` / `clearTimeout`）。注入按调用传参，不改任何全局；确需改全局的实现（如全局 `Date.now`）由测试自己 `finally` 复原。不传 `deps` 时的可见行为与今天完全相同。
- **单测的模块垫片**：`public/lib.js` 在模块顶层读 `location`，依据 public/lib.js「const PARAM_API = new URLSearchParams(location.search).get("api");」。单测文件在 `await import("../public/lib.js")` 之前先设 `globalThis.location = { search: "", origin: "http://127.0.0.1" }`，`finally` 里删掉。

### 2.2 服务端

`GET /api/health` 追加 `formats: string[]`，取值是 `Object.keys(AUDIO)`，**带前导点**（`.mp3` … `.webm`）。既有字段不动。

同一份 `formats` 在客户端派生三处，不另存一份清单：

- `accept`：`formats.join(",")` —— 带点的写法在 `accept` 属性里合法。
- 界面文案：`formats.map((f) => f.replace(/^\./, "")).join(" / ")`。
- 接受判定：文件扩展名（小写）是否在 `formats` 内，`uploadTrack` 的发送前校验用这一条。

今天的硬编码格式清单不再保留：`accept` 改由 `formats` 生成，`doUpload` 与拖入处理里的扩展名正则删除（依据 public/app.js「accept="audio/*,.mp3,.m4a,.ogg,.wav,.flac"」与「const list = [...files].filter((f) => /^audio\//.test(f.type) || /\.(mp3|m4a|aac|ogg|opus|wav|flac|webm)$/i.test(f.name));」，两处扩展名都缺 `.oga`）。

取不到 `/api/health` 时：不写 `accept` 属性（选择器不再带任何硬编码扩展名）、不显示格式与上限文案、不做前置拦截，由服务端判定。

**日志行（F6）**：一条事件一行，前缀固定 ASCII `[upload]`，四个字段固定齐全：

```text
<HH:MM:SS>  [upload] <事件键> room=<房间> file=<文件名> received=<已收字节>/<总字节> cost=<毫秒>ms detail=<原因>
```

时间前缀由 `log()` 自己加（它已按 `<HH:MM:SS>  ` 起头），调用处只传 `[upload] …` 那一段。

| 事件键 | 触发位置 | 场景 |
|---|---|---|
| `chunk-abort` | 分片路由读体失败分支（`readBuffer` reject，`Error("连接中断")`） | 分片上传中途断开 |
| `chunk-fail` | 分片路由 `fs.promises.appendFile` 失败分支 | 分片写盘失败 |
| `reject-format` | 分片 / 收尾 / 整包路由的 415 分支 | 格式不支持 |
| `reject-size` | 分片路由累计超上限的 413 分支 | 超过大小上限 |
| `reject-expired` | 分片 `offset !== 0` 无记录、收尾无记录的 410 分支 | 上传已过期 |
| `commit-fail` | 收尾 `rename` 失败分支 | 收尾写盘失败 |

样例行：

```text
15:42:07  [upload] reject-size room=9f2c file=长夜.mp3 received=83886080/88080384 cost=74120ms detail=超过 80MB 上限
```

上传三条路由（`/tracks/chunk`、`/tracks/commit`、`/tracks`）的路径、查询参数、状态码语义全部不变 —— 老客户端升级前也不会立刻失效。

### 2.3 数据流

选文件或拖入 → `doUpload` 逐个交给 `uploadTrack`（发送前校验 → `prepare` → 分片循环 → 收尾）→ 收尾 200 带回 track 视为服务端已入库 → 界面置 100% → `refreshState` 刷新歌单。

选与拖入两处都不在 `public/app.js` 里预筛文件：今天的 `doUpload` 过滤行与拖入处理里的 `isAudioFile` 过滤随之删除。文件能不能传，只由 `uploadTrack` 的发送前校验判一次；判不过的文件照样给出错误卡片，而不是被静默滤掉。

诊断流：任何阶段的失败 → 一条诊断条目进客户端的**内存环形缓冲**（上限 20 条，随页面生命周期，不落 localStorage、不落磁盘）→ 同时 `report("diag", …)` 镜像进服务端日志 → 设置页底部区块渲染最近 20 条。

## 3 受影响文件

| 文件 | 改动 |
|---|---|
| `public/lib.js` | `uploadTrack` 状态机重写：发送前校验（0 字节 / 格式 / 大小）、四出口、看门狗、阶段回调、0.99 上限、`deps` 测试缝 |

| `public/style.css` | 错误卡片与诊断区块的样式 |

**客户端读取点**：`/api/health` 仍只由 `public/engine.js` 的 `syncClock()` 发起，依据 public/engine.js「const data = await (await fetch(`${apiBase()}/api/health`, { cache: "no-store" })).json();」。

改动是在同一处把 `data.maxUpload` 与 `data.formats` 存进 `this.limits = { maxUpload, formats }`，广播 `status` 时一并带出（依据 public/engine.js「limits: this.limits,」）；`public/app.js` 读 `S.status.limits`（依据 public/app.js「const lim = S.status?.limits;」），不自行再请求第二次。

取值走广播而不直接读 `engine.limits`：浮窗与后台两种运行形态都收得到 `status` 广播，而后台引擎常驻时浮窗内没有 `Engine` 实例。「同一接口只在一处发起」仍然成立 —— `/api/health` 只有 `syncClock()` 一个发起者。

首帧时 `engine.limits` 可能仍是 `undefined`，此时按「取不到则不显示、不前置拦截」处理。

**规模层级结论**：

两处文件越过 800 行硬上限：`server/index.js` 与 `public/app.js`。两者在开批前就已越档，本批仍要往其中加代码，故各给拆分方案：

| 文件 | 档位 | 拆分方案 |
|---|---|---|
| `server/index.js` | 越过 800 行硬上限（开批前既有欠账） | 按路由族切文件：`routes/upload.js`（分片 + 收尾 + 整包上传 + `readBuffer`）、`routes/media.js`（Range 分发）、`routes/state.js`（房间状态、命令、心跳），`index.js` 只留装配与静态托管 |
| `public/app.js` | 越过 800 行硬上限（开批前既有欠账） | 按视图切模块：`views/upload.js`（上传阶段 + 错误卡片）、`views/diagnostics.js`（诊断区块）、`views/settings.js`，`app.js` 只留 `S` 状态与渲染入口 |
| `public/engine.js` | 未越硬上限 | 本批不拆；越档时按「时钟与健康检查 / 同步流 / 播放控制」切 |
| `public/lib.js` | 未越硬上限 | — |
| `public/style.css` | 未越硬上限 | — |

表里不写行数：行数随每次改动变化，写进状态文档就是一张立刻过期的快照，下一个人读到的是错的值；「越过 800 行硬上限」这个判断不会过期。

拆分由后续独立批次执行。本批只按既有结构加代码、不扩大越档幅度：`server/index.js` 的新增行落在既有三个上传路由函数体与日志调用处，`public/app.js` 的新增界面收在少数几个渲染函数里，为后续按视图迁移留出边界。

层级结论（分层）：无跨层改动 —— 前端与服务端各自独立成型，没有共享层或公共签名变更牵动第三处调用点；`public/engine.js` 进受影响文件只是新增一个取值出口，不改任何既有签名。

## 4 关键决策记录（含被否方案）

| 决策 | 选择 | 理由 | 被否的替代 |
|---|---|---|---|
| 停滞检测放哪 | `uploadTrack` 内的一个看门狗，覆盖传输与收尾 | F2 要求「不论卡在传输还是收尾」都判停滞 | 只靠 `xhr.timeout`：收尾阶段反复重试仍能在 99% 上待 5 × 30 秒 |
| 进度上限 | 传输与收尾共用 0.99 | F1 禁止在收尾期间显示 100% | 按阶段分段（传输 0–90、收尾 90–99）：收尾滑了多久用户看不出来，反而更糊 |
| 诊断来源 | 客户端内存环形缓冲 20 条，同时镜像到服务端日志 | F8 要求在界面上看到；服务端不可达时也要能看到 | 落 localStorage 跨刷新保留：F8 不要求，写盘的代价换不来场景 |
| 诊断放哪 | 设置页底部 | 面板 420×640，加 tab 会挤；只有 GM 用 | 独立 tab |
| 上限与格式来源 | `/api/health`，选择器 `accept`、界面文案、接受判定三处由同一份 `formats` 派生 | 上限已经在那里；前端再写死一份必然对不上，也违反 F9「格式清单只有一个来源」 | 前端常量：与 F9 直接冲突 |
| 前置校验放哪 | `uploadTrack` 内做，`limits` 由调用方传入 | 校验对任何调用者都成立；单测直接数 `deps.createXhr` 的调用次数，F7 的「零请求」成为可执行读数 | 放 `doUpload`：`public/app.js` 在模块顶层挂 `document` 监听（依据 public/app.js「document.addEventListener("click", (ev) => {」），node 里导入即抛错，F7 只能退回人工读数 |
| 客户端读取点 | 复用 `public/engine.js` 的 `syncClock()`，结果存 `this.limits` | 同一接口只在一处发起，浏览器不为同一份数据打两次 | `public/app.js` 自行请求：同一接口两处各取一次，两份值可能不同步 |
| 重试口径 | 每步最多重试 4 次（含首次共 5 次尝试），分片与收尾同口径 | 两种口径并存时判据写不死；分片与收尾共用同一个常量，口径只有一个来源（依据 public/lib.js「const RETRY_MAX = 4;」） | 保留两种口径：用户看不出差别，验收却给不出期望整数 |
| 服务端接受 `.oga` | 保留，并加进客户端接受列表 | 不删既有能力，新增能力优先 | 从白名单删掉 `.oga` 凑成 8 项 —— 已能传的文件会被拒，属能力回退 |
| 收尾「空文件」分支 | 分支留在代码里不动，不为它加日志事件 | HTTP 面不可达：0 字节文件不发分片，收尾时没有记录，走 410（见 §1.4）；给走不到的分支加事件键与判据，只多出一行没人能证明的验收 | 加日志事件：没有触发路径；删除该分支：改的是服务端对外判定，超出本批范围 |
| 上传中取消按钮 | 不做 | 错误卡片只负责看见，不负责中途止；没有用户提出过这个场景 | 加一个取消键 —— 没有场景的分支会连带要文案、状态与测试 |
| 上限与格式的到达路径 | `engine` 存 `this.limits`，广播 `status` 时带出，界面读 `S.status.limits` | 浮窗与后台两种运行形态都收得到状态广播；后台引擎常驻时浮窗内没有 `Engine` 实例，直接读 `engine.limits` 在浮窗里拿不到 | 直接读 `engine.limits`：浮窗形态下永远是 `undefined`，上限与格式文案与 `accept` 都不生效 |
| 超时与停滞的界面文案 | `xhr.ontimeout` 也标 `stall: true`，与看门狗共用「连接停滞，正在重试第 N 次」（依据 public/lib.js「xhr.ontimeout = () => finish(reject, Object.assign(new Error("网络超时"), { net: true, stall: true }));」） | 收尾阶段没有字节推进可言，只有超时会到点；两种到点原因对用户是同一件事：这一次等待没回音 | 为超时单列一句「网络超时」：同一段等待出现两种说法，用户以为出了两回事 |
| 玩家侧提示的文案来源 | 固定一句话，不渲染 `msg.error` | `msg.error` 是服务端原话，可能带内部字段名与错误码，F10 禁止这些东西出现在玩家侧 | 玩家视图直接复用 `noticeHtml()`：会把原始错误文本显示给玩家 |

## 5 验收对照

单测文件 `docs/batches/本地上传卡死与错误可见.test.mjs`，运行 `node --test docs/batches/本地上传卡死与错误可见.test.mjs`。界面类的 F5 / F8 / F9 / F10 用 GM 手验读数，逐条见「怎么验」列。

| 需求 | 判据 | 怎么验 |
|---|---|---|
| F1 | 第一个请求发出前有一帧 `prepare`，界面写「准备中」；收尾未返回期间 `pct ≤ 0.99`，收尾成功后为 1 | 单测：断言 `onState` 首帧 `phase === "prepare"`；收尾响应延迟时，序列里没有「phase 不是 done 且 pct = 1」的一帧 |
| F2 | 30 秒无字节推进 → 一帧 `stalled`，其 `retry ≥ 1`，界面转「连接停滞，正在重试第 N 次」 | 单测：假 XHR 不触发 progress，推进假时钟 |
| F3 | 同一步骤重试 4 次后进失败，即该步骤共 5 次尝试；超限后原因含阶段与已传百分比 | 单测：假服务端持续 500，断言该步骤 `createXhr` 被调用 5 次，且 message 含「已传 N%」 |
| F4 | 成功 / 网络错误 / 超时 / 中止四种结局都让流程继续或进失败，Promise 一定 settle | 单测：四个结局各触发一次 |
| F5 | 卡片六行（文件名、大小、阶段、已传百分比、原因、时间）；剪贴板文本包含这六项；不自动消失 | GM 手验：制造一次失败，读卡片六行；点复制读剪贴板含六项；切到别的页再回来，卡片仍在 |
| F6 | 三组事件各落一行，每行带房间、文件名、已收字节、耗时四字段 | 见下方三组触发路径 |
| F7 | 上限配 1MB 传 3MB、0 字节文件、扩展名不在 `formats` 内（`.txt`）三种输入，都拦在第一个请求之前：`createXhr` 零次调用，`onState` 零帧，`err.phase === "prepare"`；不传 `limits` 时 3MB 文件不拦（交给服务端） | 单测：`deps.createXhr` 用计数桩，三种输入各断言 0 次调用与 reject；再补一次「不传 `limits` 传 3MB 不拒」 |
| F8 | 3 条不同环节的错误按时间倒序列出，最多 20 条 | GM 手验：制造 3 条不同环节的错误，读区块的倒序与三条环节名 |
| F9 | 三处同源：选择器 `accept`、界面文案、服务端白名单都出自 `/api/health` 的 `formats`；9 种扩展名各传一次，前端不拦（选择与拖入都不过滤）、服务端不拒 | GM 手验：读选择器的 `accept` 属性含 9 项、读添加页文案 9 种，再把 9 种各传一次得 200 与歌单条目 |
| F10 | 玩家视角找不到诊断区块，也没有堆栈、错误码或内部字段名；播放出错时玩家视图出现一句固定中文提示，不含服务端原始错误文本 | GM 手验，按下面的触发路径逐步读：① 切玩家角色打开面板，读页面无诊断区块、无错误卡片、无 tab，正文检索不到「诊断」；② 制造一次音频加载失败 —— 把该房间当前曲目的文件移走（或断开服务端）后点播放；③ 读玩家视图在播放卡片之下出现「播放出了点问题，刷新页面再联系 GM 试试」；④ 读该页面文本里检索不到 `音频加载失败`、`code` 字样与任何错误码；⑤ 点「×」，提示消失；⑥ 角色切成 GM 再切回玩家，提示不重现 |

F6 的触发路径与匹配串：

| 组 | 怎么造 | 日志里该出现 |
|---|---|---|
| 分片中断 | `curl` 传一片并加 `--limit-rate 8k`，2 秒后中断 | `[upload] chunk-abort`，带四字段 |

## 8 UI / 交互决定

- 添加页常驻一行：「单个文件上限 NMB · 支持 mp3 / m4a / aac / ogg / oga / opus / wav / flac / webm」，N 与格式都取自 `/api/health`；取不到时这一行不显示，选择器也不设 `accept`，不做前置拦截。
- 上传中的阶段文字：「准备中」（`prepare`，第一个请求发出前）·「传输中」加百分比（`sending`）·「第 N 次重试」（重试期间）·「连接停滞，正在重试第 N 次」（`stalled`）·「收尾中」（`committing`）。
- 失败：一张错误卡片，六行内容（文件名、大小、卡在哪个阶段、已传百分比、失败原因、发生时间），加「复制」与「×」两个键。卡片留到用户点 ×。
- 一批结束：`已完成 N 个，失败 M 个`；M > 0 时卡片同时存在。
- 设置页底部：「诊断」区块，最近 20 条（时间 / 环节 / 原因）+「复制全部」+「清空」，仅 GM 可见。
- 玩家侧只有一句话：播放出错时，`playerView()` 在正在播放卡片之下渲染固定文案「播放出了点问题，刷新页面再联系 GM 试试」，带「×」可关；关闭后不再复现，直到下一次播放出错。
- 这一句是固定串，不拼接服务端原始错误文本 —— 原始文本可能带内部字段名与错误码，F10 不许它们出现在玩家侧。
- 触发信号（玩家侧真实可达的那条）：玩家的播放错误由引擎写进状态广播的 `error` 字段 —— 依据 public/engine.js「error: this.audio.error ? `音频加载失败（${this.audio.error.code}）` : "",」。`public/app.js` 处理 `status` 广播时按角色兜住它：非 GM 且该字段从空变非空时置 `S.playError = true`（依据 public/app.js「if (S.role !== "GM" && S.status.error && !hadError) S.playError = true;」）。
- 为什么必须边沿触发：引擎每次 `emitStatus()` 都把当前 `error` 一起播出去，错误会一直挂着；不做「从没有变成有」的判断，用户点 × 之后下一帧广播就把提示顶回来。
- 第二道来源：总线 `error` 分支同样按角色分流 —— GM 走 `toast` 带原始消息，非 GM 只把那句固定提示置上（依据 public/app.js「if (S.role === "GM") toast(msg.error, "err");」）。这条由引擎的 `command()` 发出：函数入口即 `if (!this.token) return;`，post 在同函数 catch 内（依据 public/engine.js「if (!this.token) return;」与「this.bus.post({ t: "error", error: err.message || "指令失败" });」）。令牌为空的玩家引擎发不出它，稳态下收不到，所以玩家侧的主要来源是上一条的音频错误，这条只兜其它来源。
- 原始错误串只进 GM 侧：玩家页面不出现 `音频加载失败`、错误码与内部字段名。
- 关闭时机：点「×」关闭；角色从玩家切成 GM 时一并清除 `S.playError`，否则标记一直挂着，之后切回玩家会重显一条早已过去的提示。
- 提示的显示状态记在 `S.playError`，并进渲染签名（依据 public/app.js「playErr: S.playError ? 1 : 0,」），否则状态变了界面不重绘。
- 诊断区块与错误卡片只在 GM 视图渲染，玩家侧没有入口。
