# 发布流程

> 板块：咕咕点歌台 · 设计层。本档回答一件事：一次发版由哪些动作构成，版本号写在哪，自动更新靠什么认出新版本。

## §1 方案与理由

**要解决的问题**：程序装在用户机器上，用户不会自己来拿新版，所有新版本都得靠自动更新送过去。所以「发版」不是改一个数字，而是让自动更新这条链路认得出这一次。

**方案：发版 = 三件事，缺一件新版就到不了用户手里。**

1. 把 `package.json` 的 `version` 改成这次要发的号。
2. 在 GitHub 建一次 Release，tag 名写这个号（可带 `v` 前缀，既有 tag 就是 `v1.0.0` / `v1.0.2` / `v1.0.4` 这种形态）。
3. 这次 Release 挂一个 `.zip` 资产，解开后是程序目录（`public/` / `server/` / `scripts/` / `img/` 加根目录文件）。

**为什么是这三件**：自动更新读的是 GitHub 的「最新一条 Release」——标签号当新版号，`.zip` 资产当下载包，本地 `package.json` 的版本号当当前版本。三者的接口关系写在 §2。

**先例**：本仓没有发布流程档，本档是第一个。同类机制的先例在代码里，逐条列出如下。

| 先例 | 坐标 | 名称（原文） | 现有用法 | 本档怎么处置 |
|---|---|---|---|---|
| 版本号读取 | `server/update.js` | `currentVersion()` | 从 `package.json` 取当前版本 | 沿用：package.json 是唯一版本来源 |
| 更新检查 | `server/update.js` | `checkForUpdate()` | 读 Releases 最新一条 | 沿用：发版必须建 Release |
| 发布前自检 | `tools/check-release.mjs` | `npm run check-release` | 扫隐私与路径问题，用退出码判定 | 沿用：发版前必跑 |
| 设计档形态 | `docs/design/本地上传与错误诊断.md` | 九章结构 | 方案 / 契约 / 文件 / 决策 / 判据 / 用例 / 边界 / 界面 / 集成 | 沿用：本档同用九章 |

**公开源调研**：`doc_search` 查「发布流程 / 版本号 / 发版 / GitHub Release / 自动更新」→ 无命中；项目 manifest 的 `index.publicRepos` 为空，没有声明任何外部公共仓。结论：本主题无先例文档可对齐，本档从代码事实起头。

**数据事实**：本设计不依赖库数据（不读库、不读行）。要读的是仓库状态，已读三项：版本号写在 `package.json` 顶层的 `version` 字段、由 `currentVersion()` 运行时读出（取值每次发版都变，本档不记）；`git tag` 形如 `v1.0.0` / `v1.0.2` / `v1.0.4`；OBR 扩展清单版本写在 `public/manifest.json` 的 `version` 字段，与程序版本是两条线。

**每个新增判断的依据**（逐条给来源，引自本仓文件原文）：

- 版本号只认 `package.json`：依据 `server/update.js`「return JSON.parse(fs.readFileSync(path.join(ROOT, "package.json"), "utf8")).version || "0.0.0";」
- 发版必须建 Release：依据 `server/update.js`「const r = await fetch(`https://api.github.com/repos/${REPO}/releases/latest`, { headers });」
- 新版号取 Release 的标签：依据 `server/update.js`「const tag = String(j.tag_name || "").trim();」
- Release 必须挂 `.zip`：依据 `server/update.js`「const asset = (j.assets || []).find((a) => /\.zip$/i.test(a.name));」
- tag 带不带 `v` 都认：依据 `server/update.js`「const pa = String(a).replace(/^v/, "").split(".").map(Number);」
- 没挂 zip 时下载明确失败：依据 `server/update.js`「if (!url) return { ok: false, error: "没有找到下载地址" };」
- 发布前自检是门，不是提醒：依据 `tools/check-release.mjs`「process.exit(fatal.length ? 1 : 0);」

## §2 接口契约

### 2.1 版本号

单一来源：`package.json` 顶层的 `version` 字段。读取点的依据引文见 §1「每个新增判断的依据」第一条，本处不再逐字引用该字段的取值——取值每次发版都变，引进来就是一条会过期的引文。运行中由 `server/update.js` 的 `currentVersion()` 读出，经 `GET /api/health` 与 `GET /api/update` 送到界面。

不新增第二份版本文件，也不在代码里写死版本字符串。

### 2.2 发版三件套的契约

| 项 | 谁读它 | 契约 |
|---|---|---|
| `package.json` 的 `version` | `currentVersion()` | 当前版本；三段数字 `X.Y.Z`，可被 `cmp()` 解析 |
| Release 的 `tag_name` | `checkForUpdate()` | 新版号；可带 `v` 前缀，比较前被剥掉 |
| Release 的 `*.zip` 资产 | `checkForUpdate()` → `downloadUpdate()` | 下载地址；没有匹配资产时下载返回「没有找到下载地址」，不落半包 |

### 2.3 发布包结构

解压后必须是程序目录本身，或只多套一层含 `package.json` 的目录——依据 `server/update.js`「if (entries.length === 1 && fs.existsSync(path.join(PENDING, entries[0].name, "package.json"))) {」；自动更新会把那一层剥掉。

启动时替换的范围固定为 `public` / `server` / `scripts` / `img`（依据 `server/update.js`「const SWAPPABLE = ["public", "server", "scripts", "img"];」），另加根目录的 `README.md` / `README.txt` / `一定要先看README！.txt` / `LICENSE` / `package.json`。`runtime/` 与 `data/` 不动。

### 2.4 发版动作顺序

1. 本批改动全部提交到 `main`。
2. `npm run check-release`，退出码 0。
3. 改 `package.json` 的 `version`，单独提交这一行。
4. 建 Release：tag 写 `v<version>`，挂发布包 zip。
5. 用户侧：`/api/update/check` 读到 `hasUpdate: true`，下载完成后界面出「新版本 X 已下载」横幅，关窗重启时自动替换。

## §3 受影响文件

| 文件 | 本批动作 | 规模层级 |
|---|---|---|
| `package.json` | `version` 一行 1.0.4 → 1.0.5 | 未越硬上限 |
| `.gitignore` | 新增 `.thincoder/`（本机 agent 工作目录，会话缓存，不属项目） | 未越硬上限 |
| `tools/check-release.mjs` | 本机数据目录改为「内容不扫、存在仍告警」：新增 `LOCAL_ONLY_DIRS` / `LOCAL_ONLY_PREFIXES` / `isLocalOnly()`，`walk()` 的跳过判据换成 `skipDir()` | 未越硬上限 |
| `docs/design/发布流程.md` | 新建本档 | 文档，不判 |

依据 `tools/check-release.mjs`「const skipDir = (name) => SKIP_DIRS.has(name) || isLocalOnly(name);」

分层结论：无跨层改动。版本号只有一处写点，没有第二处调用点要跟着改；`tools/check-release.mjs` 的改动只在文件内部换跳过判据，不跨模块。

规模结论：四个文件都没有越过 800 行硬上限，不涉及拆分。

## §4 关键决策

| 决策 | 理由 | 被否的方案 |
|---|---|---|
| 版本号只写 `package.json` 一处 | 读取点只有 `currentVersion()`；两处版本号迟早不同步，而不同步时自动更新会认错新版 | 在 `server/update.js` 里另写常量；在 `public/manifest.json` 里记程序版本 |
| tag 用 `v<version>` | 与既有三个 tag 同形；`cmp()` 剥掉 `v`，带不带都能比 | 纯数字 tag（能跑，但与历史形态不一致） |
| 发版必建 Release 并挂 zip | 更新检查只认 Releases 接口，不读仓库文件；不改这条链路就只能让用户手动重下 | 让更新改读仓库里的 `package.json`（要改 `update.js`，本批不做） |
| `public/manifest.json` 的 `3.1.0` 不随本批动 | 它是扩展清单版本，与程序版本是两条线；本批要涨的是程序版本号 | 两个版本号一起涨——会把扩展版本线打乱 |
| 发版前跑 `check-release` | 它拦的是内网地址、本机路径、写死后端地址、清单根路径：这些一发布就泄露或让插件失效 | 不跑、靠人记（会被忘） |

## §5 验收判据

对应本批两条要求（版本号上调 / 发版口径落档）。每条都给出可执行验法。

| # | 判据 | 验法 |
|---|---|---|
| A1 | `package.json` 的 `version` 为 `1.0.5` | `node -e "console.log(require('./package.json').version)"` 输出 `1.0.5` |
| A2 | 发布前自检通过 | `npm run check-release` 退出码 0 |
| A3 | 本档在盘且自洽 | `doc_check(mode:"gate")` 首行为 `DOC-CHECK GATE: PASS` |
| A4 | 版本号只有一处写点 | 在代码与配置面（`*.js` / `*.mjs` / `*.json`）检索 `1.0.5`，只出现在 `package.json` |

## §6 用例表

| 类型 | 输入（Release 状态 / 本地版本） | 期望 |
|---|---|---|
| 正常 | tag `v1.0.5`，本地 1.0.4，挂了 zip | `hasUpdate: true`；下载后解压到 `.update/pending` |
| 正常 | tag `1.0.5`（无 `v`），本地 1.0.4 | 同上，新版号被正确解析 |
| 边界 | tag `v1.0.5`，本地也是 1.0.5 | `hasUpdate: false`，不提示 |
| 边界 | 压缩包里多套一层目录 | 解压后自动剥掉那一层 |
| 错误 | tag 有了但没挂 zip | 下载返回「没有找到下载地址」，不落半包 |
| 错误 | 本地版本高于 Release（回退安装） | `hasUpdate: false`，不给用户降级 |

## §7 边界

本档不覆盖、本批也不做：

- 不打 tag、不建 Release、不生成发布包——那是发版动作本身，发布时由主 agent 执行。
- 不改 `server/update.js` 的检查与替换逻辑。
- 不动 `public/manifest.json` 的扩展清单版本。
- 不做下载包签名与校验和（不验签，属后续安全项）。
- 不把 GitHub Pages 纳入发版：该工作流是手动的可选发布，正常发版不需要它（依据 `.github/workflows/pages.yml`「默认不随推送自动运行」）。

## §8 界面与交互

本批无界面改动。发版之后用户的可见变化由既有界面承担：更新横幅「新版本 X 已下载」与「关闭这个窗口，再双击「点这个启动程序」」提示（`public/app.js` 的 `upd` 状态块），本批不改文案与位置。

## §9 集成测试设计

本仓没有集成用例索引档，也没有集成套件（欠账 #2 承接，复启条件为项目转正式版前）。故本批对索引的差量为：无行可破、无行可删、无行可增。

不新增集成用例的理由：版本号与发版口径不产生新的业务可观察结果。用户能看到的「有新版本」由既有更新横幅承担，而它当前没有自动验收入口——如实列在这里，不以「索引未建」当理由。

验收止于 §5 的读数与收口时一次人工确认。
